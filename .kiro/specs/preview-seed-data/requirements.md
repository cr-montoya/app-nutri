# Requirements: Preview Seed Data

## Objective

Every Vercel/Neon preview deployment currently starts with an empty database: a reviewer opening a PR's preview has to manually create an organization, invite/create users for each role, register professionals, add patients, and schedule appointments before they can exercise anything. This spec automates that by hooking a seed step into the existing `migrate-preview` job (`infra-migration-pipeline`) so every preview branch is populated with realistic, synthetic, multi-role sample data immediately after migrations apply — with a structural guarantee that this can never run against the production database.

## User story

As a developer or reviewer opening a PR's preview deployment, I want the preview database automatically populated with sample organizations, users, professionals, patients, and appointments, so that I can log in and exercise the app's flows immediately, without recreating test data by hand on every preview.

## Acceptance criteria (EARS)

- **REQ-001**: WHEN the `migrate-preview` job successfully applies migrations to a PR's Neon preview branch, THE SYSTEM SHALL run a seed step against that same preview branch's database immediately afterward, reusing the same resolved connection string `migrate-preview` already fetched (no second Neon API lookup).
- **REQ-002**: THE SYSTEM SHALL ALWAYS refuse to execute the seed script unless it is invoked with an explicit preview-confirmation environment variable that only the `migrate-preview` job step sets, so no other invocation path (a developer's local shell, a copy-pasted command, any future job) can run it by accident.
- **REQ-003**: THE SYSTEM SHALL NEVER be referenced from the `migrate-production` job; `migrate-production`'s job definition in `.github/workflows/migrate.yml` must not invoke the seed script under any condition.
- **REQ-004**: WHEN the seed step runs AND a seed organization from a prior run already exists on that database (located via the stable, well-known slug in REQ-005), THE SYSTEM SHALL delete that organization and every row that references it before inserting fresh data, so repeated pushes to the same PR (each re-triggering `migrate-preview`) never accumulate duplicate or stale rows. WHEN no such organization exists yet (a database seeded for the first time), THE SYSTEM SHALL skip deletion and proceed directly to inserting fresh data.
- **REQ-005**: THE SYSTEM SHALL create exactly one seed `Organization` with a stable, hardcoded `slug` (not randomly generated), so a reviewer can navigate directly to `/<slug>/...` on any preview without reading generated output first.
- **REQ-006**: THE SYSTEM SHALL create, within the seed organization, one `User` + `Membership` for role `ADMIN`, one for role `FRONT_DESK`, and two for role `NUTRITIONIST` (each NUTRITIONIST membership paired with its own `Professional` profile, per the schema's 1:1 constraint), every user having a fixed, documented email and the same fixed password, hashed with the project's existing argon2id scheme (`src/lib/auth.ts`), so a reviewer can log in as any role without a signup/invite flow. This fixed password SHALL be committed in plain sight in the seed script's source (not treated as a secret) — a deliberate, accepted decision, not an oversight: it only ever protects fully synthetic data on ephemeral, isolated Neon preview branches (REQ-002/REQ-003 make it structurally unreachable from production), so the usual reasoning against hardcoded credentials does not apply here.
- **REQ-007**: THE SYSTEM SHALL create at least 8 `Patient` records in the seed organization with varied, clearly-fictitious demographic data, including at least one archived (`archivedAt` set) patient, so list, search, and archive-toggle flows all have data to exercise.
- **REQ-008**: THE SYSTEM SHALL create `Appointment` records in the seed organization covering all five `AppointmentStatus` values, spread across both seeded `Professional`s, with the following temporal placement: `SCHEDULED` and `CONFIRMED` appointments SHALL be placed today or in the next few days (future, relative to the seed run's execution time); `COMPLETED`, `CANCELLED`, and `NO_SHOW` appointments SHALL be placed in the recent past (before the seed run's execution time) — reflecting that these are terminal outcomes of appointments that already happened, and ensuring at least one non-empty and one empty day are both visible on the default calendar view without further navigation.
- **REQ-009**: THE SYSTEM SHALL ensure every seeded `Appointment` independently satisfies `phase-1c-appointments-calendar`'s own constraints (duration 5–480 minutes, no overlapping active appointments for the same professional), so the seed step never fails against the database's exclusion constraint or the application's validation bounds.
- **REQ-010**: WHEN the seed step completes successfully, THE SYSTEM SHALL print the seed organization's slug and each seeded user's email + role to the job log, and SHALL NEVER print any password, password hash, or the patient/appointment data bodies, consistent with `.agents/rules/no-plaintext-clinical-data.md`'s intent even though this is synthetic, not real, data.
- **REQ-011**: WHEN the seed step fails for any reason, THE SYSTEM SHALL exit non-zero, causing the `migrate-preview` check to fail visibly, so a broken seed is never silently swallowed into an apparently-green but unseeded preview.
- **REQ-012**: THE SYSTEM SHALL NEVER include any real person's name, contact detail, or other real personal data in the seed data — every seeded value SHALL be clearly synthetic (obviously fictitious names, `@example.com`-style emails).
- **REQ-013**: THE SYSTEM SHALL ALWAYS run at most one `migrate-preview` job (and therefore at most one seed step) concurrently per pull request, superseding/cancelling an in-progress run when a new commit is pushed to the same PR, so REQ-004's delete-then-insert logic never races against a second, overlapping run against the same Neon preview branch.

## Out of scope

- A manual, locally-invoked `pnpm seed` convenience command — this phase covers automatic preview seeding only, per explicit product decision. A manual entrypoint is a separate, later increment, not part of this spec.
- Seeding production data, or any change to `migrate-production`'s behavior beyond confirming it's untouched.
- Seeding Phase 2 models (`ClinicalHistory`, `Consultation`, `AnthropometricMeasurement`, `NutritionalPlan`) — not yet implemented in the schema.
- Cleaning up production tables before launch — a separate, later, manual operational step the user already identified as out of scope for this spec.
- Changing `migrate-preview`'s Neon branch lookup, retry budget, or credential handling — reused as-is from `infra-migration-pipeline`.
